# Rust metric rules

Rules version: **2.0**.

The [generic metric rules](generic-metric-rules.md) define Cognitive scoring and function ownership. Apply the [recursive composition rules](generic-metric-rules.md#recursive-composition) at every nesting level.

The Rust analyzer copies the parser tree, including node types, child roles, relevant tokens, and source locations. It recovers recognized macro arguments before assigning local contributions to `score.cognitive`. Shared aggregation sums them by owner. [Shared analysis contract](generic-metric-rules.md#analysis-structure-and-responsibilities)

## Function ownership

* `fn` items, `impl` methods, and closures follow the generic function ownership rules.
* An `async` block preserves the current function owner.
* Macro invocations and definitions create no function records.
* Rust `cfg` attributes leave the written source in scope.

## Cognitive Complexity

### Language constructs

Apply the [generic Cognitive rules](generic-metric-rules.md#cognitive-complexity) to these Rust constructs.

* `if` and `else if` are conditions. `if let` follows the same rules.
* `loop`, `while`, and `for` are loops. `while let` follows the same rules.
* `match` is a selection. Patterns separated by `|` within one arm belong to that arm. A guard adds no points of its own. Visit its written expressions recursively.
* Labeled jumps use `break 'label` or `continue 'label`.
* The propagation operator `?`, pattern bindings, and `yield` add no points of their own. Visit their children under the ordinary rules.

| Rule | Example | Score |
| --- | --- | ---: |
| Simple match | `fn f(x: i32) { match x { 1 => first(), 2 => second(), _ => third() } }` | 1 |
| Match with a condition in one arm | `fn f(x: i32) { match x { 1 => { if ready {} }, _ => {} } }` | 3 |
| Loop with a condition | `fn f() { loop { if ready {} } }` | 3 |
| Labeled loop with a condition and jump | `fn f() { 'outer: loop { if ready { break 'outer; } } }` | 4 |

### Refutable declaration with a failure body

`let pattern = initializer else { body };` contributes `1 + depth` on the `let_declaration` node. The pattern and `else` add no separate point. Visit the initializer at the incoming depth and the failure block at depth + 1. Ordinary `let` declarations have zero points of their own.

### Macro definitions and invocations

The invocation itself adds zero points and preserves the enclosing depth. Analyze recognized written arguments under the ordinary rules. Separate arguments form separate logical sequences. Exclude macro definition patterns, templates, and code that would be generated by expansion.

The analyzer parses recognized argument syntax from the parser's `token_tree` into Analyze AST children before scoring. It maps the resulting nodes to original source locations and counts each written construct once.

* Empty contents have no argument operations. A complete Rust expression or a complete list separated by commas or semicolons supplies ordinary arguments. A list uses one separator kind at its own level. A comma list may have a trailing comma. Separators within an expression remain part of that expression.
* If the whole input is not an expression list, a complete expression followed by a structural pattern with written fields or `..` and an optional guard is recognized as distinct roles. The expression and guard have independent ordinary argument contexts. The pattern, its guard marker, and separator contribute no points of their own. A parser-only `match` wrapper contributes nothing.
* A complete list of `PAT = EXPR => BODY` members exposes the pattern, input expression, and body expression as distinct roles. Members are comma-separated, with an optional trailing comma. A complete block body may omit the comma. Input and body use separate ordinary argument contexts. The binding, arrow, and member add no depth or points of their own.
* A complete comma-separated list containing at least one type that is not a complete expression exposes its members as types. Embedded expressions retain ordinary scoring. Expression lists take precedence.
* A complete list of initialized const and static value declarations exposes the written declarations with their types and initializers. Written constructs follow their ordinary scoring rules. Incomplete or mixed lists remain unsupported.
* Recognize each whole argument recursively, including nested macros. Use parsed fragment boundaries to identify arguments.
* Invocation delimiters, grouping parentheses, and argument separators add no points. Block expressions inside the argument list follow the ordinary block rules.
* Other macro input grammars require structural recognition in the analyzer. For example, a repetition form can expose its value and count expressions as Analyze AST children. Apply ordinary scoring rules to those children.
* Identify calls from recognized syntax. Patterns, quoted templates, and custom macro languages can resemble executable expressions.

A recognized invocation is within the ordinary scoring scope. If the argument syntax is unsupported, issue a diagnostic under the [shared coverage rules](generic-metric-rules.md#coverage-and-exclusions). The reported total excludes contributions on affected physical lines.

In this example, the invocation and `verify()` contribute zero. The logical sequence beginning with `&&` contributes one point.

```rust
fn condition(ready: bool) {
    assert!(ready && verify());
}
// Cognitive: 1
```
